# codespot：面向 AI 编码时代的国产化静态代码扫描工具
## ——项目立项、设计与交付情况汇报

> 汇报日期：2026-09-23 · 项目状态：已交付并投入试用（v1）

---

## 一、背景：为什么需要 codespot

### 1.1 AI 编码规模化带来的新风险面

随着 AI 辅助编码（AI Coding）在全行的普及，大量代码由开发人员借助行内外 AI 工具生成。AI 生成的代码在提升效率的同时，引入了三类传统流程难以覆盖的风险：

- **质量风险**：AI 代码常见逻辑缺陷、未使用代码、错误处理缺失等问题，人工评审疲劳后难以逐一把关；
- **安全风险**：硬编码密钥、SQL 注入、不安全的随机数与反序列化等漏洞模式在 AI 生成代码中出现频率显著偏高；
- **供应链风险**：AI 倾向推荐"能跑就行"的依赖版本，旧版本依赖携带已知 CVE 的情况时有发生。

### 1.2 现有手段的三个缺口

| 缺口 | 说明 |
|------|------|
| **仅靠 AI 模型扫描不够全面** | 大模型审查是非确定性的：无规则库兜底、无 CVE 数据库、无密钥特征库，存在漏报与幻觉；且逐文件人工喂给模型的用法无法工程化 |
| **传统扫描工具无法融入 AI Agent 生态** | 商业与开源扫描器（如 SonarQube 系）面向 CI/服务器架构设计，需要部署服务端，无法被 AI Agent 在本地按需调用，更谈不上"扫描→报告→修复"的闭环 |
| **国产化与自主可控要求** | 主流商业扫描工具均为国外产品，且许可证条款趋紧（如 SonarSource 2024 年底将分析器改为非开源的 SSALv1 许可，明确限制"用非捆绑 AI 摄取其分析结果"）；核心安全工具依赖外部供应商存在供应链与合规风险 |

### 1.3 项目定位

建设一个**纯本地运行、原生融入 AI Agent 生态、全栈开源引擎、代码完全自主可控**的静态代码扫描 skill（命名 codespot）：AI 写完代码 → codespot 本地扫描 → 产出 AI 可读报告 → Agent 辅助修复 → 重扫验证，形成完整质量闭环。

## 二、解决方案与方案设计

### 2.1 两轮可行性调研（结论先行）

项目启动前完成了两轮系统性技术调研（详见《可行性调研报告》，含 30+ 组件的当日实测核验数据），核心结论：

1. **Sonar 系分析器路线不可行**：官方 CLI 必须连接其云端/服务器；分析器许可证已改为 SSALv1，其中"禁止用非捆绑 AI 摄取分析结果"条款与本项目"AI 读报告并修复"的核心场景直接冲突；
2. **推荐路线（已采纳）**：以**干净许可的开源引擎组合**为主体（MIT/Apache/LGPL），架构上做成"多引擎适配器 + 统一报告 + AI 修复闭环"，规则保真度高的 Sonar 原生引擎留作实验选项未启用；
3. **许可合规**：所有引擎采用"运行时从官方源下载、不随工具分发"模式，对 LGPL 组件零额外义务；对 Semgrep（规则许可限内部使用）与 TruffleHog（AGPL）明确"仅内部使用"边界并写入文档。

### 2.2 总体架构

```text
用户/Agent："扫一下代码"
      ↓
┌ codespot 主控 CLI（Python 标准库，零依赖）─────────────┐
│  git 范围计算：未提交 → 未推送 → 全量（自动降级）      │
│  引擎注册表驱动调度：并行执行、失败隔离                │
│  ┌ 10 个引擎适配器（统一契约）────────────────────┐   │
│  │ 密钥: gitleaks（常开）/ TruffleHog（可选）     │   │
│  │ Python: ruff + bandit                          │   │
│  │ JS/TS: oxlint（快）+ ESLint/sonarjs（深）      │   │
│  │ Java: PMD（源码）+ SpotBugs/FindSecBugs（字节码）│  │
│  │ SQL: SQLFluff   跨语言语义: Semgrep CE         │   │
│  │ 依赖漏洞: OSV-Scanner（离线库/在线）            │   │
│  │ AI 语义审查: agent 驱动（可选）                 │   │
│  └───────────────────────────────────────────────┘   │
│  统一 issue 归一化 → severity 四级 → CS 编号           │
│  双报告：report.json（Agent 接口）/ report.md（人读） │
└──────────────────────────────────────────────────────┘
      ↓
Agent 呈现修复选项 → 修复 → 重扫验证（≤3 轮）→ 汇总
```

**关键设计**：引擎适配器统一契约（输入/输出/退出码），新增引擎零改基座；人读界面统一 codespot 品牌（稳定 CS-xxxxx 规则编号，不暴露底层工具名），Agent 接口保留完整内部字段保证修复精度；项目级三层规则配置（原生配置文件 > codespot 配置 > 内置默认）。

### 2.3 工程管理

采用 **OpenSpec 规格驱动开发**：每个功能批次先产出提案/行为规格/设计/任务清单并校验，再实施、验收、归档——全程共 **8 个变更批次**，规格即文档，行为可追溯。

## 三、核心能力一览（产品视角）

### 3.1 支持的语言与规则规模（实测口径）

| 语言/维度 | 质量/规范规则 | 安全能力 | 依赖/供应链 |
|---|---|---|---|
| **Python** | ruff **503 条**启用 | ruff S 族 + bandit 32 插件 | OSV-Scanner 实时 CVE |
| **JavaScript/TypeScript** | oxlint **335 条** + sonarjs **约 215 条**（双层去重） | 同左 + Semgrep | OSV-Scanner |
| **Java** | PMD **213 条**（源码级，无需编译） | SpotBugs 约 470 模式 + FindSecBugs **144 安全检测器**（CWE 标注，字节码级数据流） | OSV-Scanner |
| **SQL** | SQLFluff **约 48 条**（自动方言探测） | — | — |
| **Go/C#/Kotlin/Ruby/PHP/Rust/Swift/Scala** | — | Semgrep **2800+** registry 规则（taint 分析） | OSV-Scanner |
| **密钥（全语言）** | — | gitleaks **222 条**（常开）；TruffleHog **800+ 检测器**（可选深度层） | — |

### 3.2 亮点能力

- **增量扫描**：默认只扫"未提交/未推送"的改动面，秒级~分钟级反馈，贴合 AI 高频迭代节奏；
- **密钥检测与活体验证**：常开层 222 条规则全语言拦截硬编码密钥（报告强制脱敏）；可选启用 TruffleHog 深度层（800+ 检测器，覆盖小众与国产 SaaS 密钥格式），其**密钥活体验证**（联网确认密钥是否仍有效）默认关闭以保证离线与合规，可按需手动执行——发现真实密钥时工作流强制"先轮换、后清理"；
- **依赖漏洞（SCA）**：OSV-Scanner 查询 Google OSV 漏洞库，支持**离线漏洞数据库**（`update-db` 一键下载，断网环境可用），每条发现附升级目标版本；
- **AI 语义审查（首创亮点）**：`scan --engine ai` 产出审查计划，由 AI Agent 按计划做静态规则抓不到的语义级审查（逻辑错误/并发竞态/错误处理缺口/跨文件不一致），结果经校验合并进统一报告——**工具规则 + AI 语义双引擎互补**，直接回应"仅 AI 扫描不全面"的痛点；
- **AI 修复闭环**：按严重级选择修复范围 → Agent 逐条判断合理性并修复 → 重扫验证 → 已修复/跳过/剩余三类汇总；
- **治理与品牌**：CS 编号品牌层、三层规则删减/调参、severity 覆盖、误报白名单、`selftest` 九夹具回归自检；
- **离线可用**：联网做一次 setup + update-db 后，除 Semgrep 外全部能力离线运行。

## 五、验证效果

### 5.1 开源项目实测（三仓库、零引擎失败）

| 仓库 | 语言/规模 | 耗时 | 发现 | 验证要点 |
|---|---|---|---|---|
| psf/requests | Python·128 文件 | 84s | 783 条 | **依赖漏洞真实命中**：vendored idna 旧版 CVE（附升级版本） |
| expressjs/express | JS·212 文件 | 127s | 714 条 | JS 双层（oxlint+sonarjs）互补**无重复报告** |
| jhy/jsoup | Java·318 文件 | 265s | 4791 条（**53 critical**） | 最复杂链路全通：pom 探测→Maven 编译→SpotBugs 深度层命中 **XXE、SSRF、XPATH 注入、可预测随机数**（均带 CWE 编号） |

（完整报告见 `docs/validation-report.html`）

### 5.2 内部项目实战（kaipanla 行情项目）

- 全量扫描检出 **54 条依赖漏洞**，其中 critical：PyMySQL SQL 注入（修复版本 1.1.1）、anyio TLS 主机名校验缺陷——均为真实可核实问题；
- 检出 7 条 ruff S608 SQL 注入 critical（增量扫描未覆盖的历史文件）；
- 修复循环实战：自动定位并修复 `zip()` 缺 `strict`、NaN 判定语义模糊、`global` 状态反模式等真实缺陷，重扫验证无回归。

### 5.3 质量与回归

`selftest` 九夹具回归自检 **10 引擎全绿**（含 schema 校验、品牌隔离断言、脱敏断言）；人读报告经引擎名检索验证零泄漏。

## 六、ROI 分析

**收益侧（年度视角估算）**：

1. **许可费用节省**：对标商业 SAST/SCA 组合（SonarQube Developer + SCA 模块，组织级年费常见 10~30 万元量级）→ codespot 许可成本为 0；
2. **评审效率**：AI 修复闭环将"发现→修复→验证"从人工小时级压缩到分钟级；按每开发者每月拦截/修复 5 处问题、每次节省 30 分钟保守估算，20 人团队年节省约 **250 人时**；
3. **风险规避（主要价值）**：一次密钥泄漏或供应链漏洞事件的处置成本（应急响应、监管报告、客户影响）远超本项目全部投入；密钥检测在写入仓库**之前**拦截，属于成本最低的控制点；
4. **国产化合规收益**：核心工具链自主可控，规避 Sonar SSALv1 类许可风险与外采供应链风险，满足自主可控考核要求；
5. **能力复用**：适配器契约 + 注册表机制使新增引擎成本降至约半天/个，AI 语义审查机制可平移至其他 Agent 场景。

**投入侧**：约 1 人天人工 + 2000 万 tokens 以内的 AI 算力（内部套餐计价不足百元级） + 零许可费；后续维护为引擎版本升级（改注册表版本号即可）与规则微调（项目级配置，无需改代码）。

**结论**：本项目投入极低、交付完整、验证充分，单次风险事件的避免即可覆盖全部成本，建议在团队内推广使用并纳入 AI 编码标准工作流（AI 生成 → codespot 扫描 → 修复 → 提交）。

## 七、边界与后续建议（如实说明）

- Semgrep 规则许可限内部使用，工具不可对外销售/分发（已写入文档边界）；
- Windows 支持需约一天适配（Semgrep 在 Windows 需 WSL2）；当前在 macOS/Linux 验证充分；
- TruffleHog 密钥活体验证默认关闭（合规考虑），需要时手动开启；
- AI 语义审查发现为建议性（附 confidence），最终由人决策。
